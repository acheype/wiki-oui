# WikiOui — Synthèse de conception

WikiOui est un moteur de wiki : des sites collaboratifs dont chaque page est écrite en MDX et éditable en ligne. Refonte de YesWiki sur une stack moderne. **L'ergonomie est prioritaire** (composants beaux, fluides, ergonomiques).

Ce document est la **vue d'ensemble** : ce que chaque version apporte, et l'architecture transverse. Le détail vit ailleurs — glossaire du domaine dans [`../CONTEXT.md`](../CONTEXT.md), specs de chantier dans [`component-builder.md`](component-builder.md), [`forms.md`](forms.md), [`entries-view.md`](entries-view.md) et [`permissions.md`](permissions.md), décisions structurantes dans [`adr/`](adr/).

## Stack

Next.js (App Router) · React 19 · TypeScript · Prisma · PostgreSQL · shadcn/ui + Tailwind · CodeMirror 6 (éditeur) · pipeline MDX (`next-mdx-remote` + `remark-gfm` + `mdx-annotations`) · **Zod** (contrat runtime) · `react-hook-form` + `dnd-kit` (formulaires) · Nodemailer (courriels) · Leaflet, FullCalendar, Embla (vues de fiches) · sharp (images) · **BetterAuth** (authentification seule, ADR 0023) · Vitest · **pnpm**.

## v0.1 — MVP

CRUD de pages par slug · routing page/handler natif Next · handlers `show`, `edit`, `revisions` · rendu MDX bridé · composants intégrés `<Menu>` (liste imbriquée → menu multi-niveaux, ADR 0010) et `<Button>` · historique (toutes révisions) + diff + restauration · pages spéciales de layout (roue crantée de `page-rapide-haut` vers les pages de configuration du layout) · éditeur riche CodeMirror (barre d'outils markdown, listes de tâches, modale de lien, outils contextuels ancrés au curseur : édition de lien, tableaux) · double-clic sur le contenu pour éditer · tags · « hard delete » (suppression définitive).

## v0.2 — Upload de fichiers & authoring de composants

### Upload de fichiers

**Trois portes, un pipeline** : bouton **Uploader** de la barre d'outils · **drag & drop** dans l'éditeur (insertion à la position du pointeur au moment du drop) · **collage** (fichier copié ou capture d'écran ; nom généré `capture-AAAA-MM-JJ.png` si le presse-papier est anonyme). Un fichier à la fois — plusieurs fichiers ou un dossier → toast clair. Le fichier part vers `POST /api/files` pendant que la modale affiche nom, taille et **progression d'envoi** (service d'API + `xhr.upload.onprogress` : une Server Action ne sait pas exposer la progression — ADR 0012). Puis selon la **famille** du fichier :

- **image** → `<Image>` : alignement (texte en dessous, gauche, centre, droite), taille (originale ou spécifiée), texte alternatif pour les personnes malvoyantes ; en paramètres avancés : lien web associé au clic · effets graphiques (bord blanc, ombre portée, agrandissement au survol) · clic sur l'image pour l'afficher en grand dans une modale · texte affiché au survol ;
- **pdf** → mini-choix « intégrer le contenu dans la page » (`<Pdf>`) ou « insérer un lien de téléchargement » (`<FileLink>`) ;
- **other** → `<FileLink>` : un lien de téléchargement affichant le nom et la taille du fichier ; champs : texte du lien, texte affiché au survol.

Annuler la modale **juste après l'upload qui a créé le fichier** supprime le fichier (toast « rien n'a été conservé ») ; annuler une réédition ou une insertion depuis le menu ne supprime jamais rien.

**Stockage** (ADR 0012) : répertoire `files/` à la racine — **le répertoire fait foi**, pas de table Prisma ; noms slugifiés, collision → suffixe numérique ; orphelins conservés (bibliothèque du wiki) ; accès via `lib/files.ts` (adaptateur S3 enfichable au backlog). Service par `GET /api/files/[name]` avec `nosniff` partout, `CSP: sandbox` sur les svg, `Content-Disposition: attachment` sur la famille `other` — seul le segment `api` est réservé, il regroupe tous les services d'API.

**Configuration** (`wiki.config.ts`) : `upload.maxFileSize` (défaut 10 Mo), `upload.maxImageSize` (défaut 2 Mo), `upload.allowedExtensions` groupées **par famille** — la famille route vers le bon composant et filtre les combobox `file-list`. Par défaut : **image** = jpg, jpeg, png, gif, webp, avif, bmp, tif, svg ; **pdf** = pdf ; **other** = la centaine d'extensions bureautiques, audio, vidéo et archives héritée de YesWiki (liste dans la config).

### Authoring de composants (ComponentBuilder)

Les composants sont des composants MDX placés dans `/components/wiki` (autodécouverts par le registre, ADR 0002). Un composant doté d'un **descripteur YAML co-localisé** (ex. `button.yaml`) apparaît dans le menu « Composants » de l'éditeur ; le sélectionner ouvre son **ComponentBuilder** : une modale de paramétrage **autogénérée depuis son descripteur YAML** (champs, types, défauts) — aperçu du rendu en haut, champs en dessous (les champs `advanced` derrière « paramètres avancés »). Le composant `.tsx`, lui, est du React **sans contrat** (client ou serveur) : il fournit l'aperçu, et sa cohérence avec le descripteur est **vérifiée par signature** au build et en dev (ADR 0013). L'aperçu est produit par le **vrai pipeline** de rendu de pages : l'iframe de la modale charge `GET /api/render?source=…` (debounce, hauteur `previewHeight`), une page **nue** — hors du groupe de routes `(site)` qui porte le chrome du site — donc hydratée et fidèle : ce que montre l'aperçu est ce que la page rendra, erreurs comprises. (Un `route.ts` + `renderToStaticMarkup` est impossible : les composants client ne se sérialisent pas hors du pipeline RSC.) Spécification du ComponentBuilder et du YAML : [`component-builder.md`](component-builder.md) (avec table de traduction depuis le format YesWiki, [`reference/yeswiki-actions-builder.md`](reference/yeswiki-actions-builder.md)).

Exemple du bouton : texte · lien (web ou nom d'une page du wiki) · texte affiché au survol · icône via le **sélecteur d'icônes Iconify** · couleur (défaut, primaire, secondaire 1, secondaire 2, succès, info, attention, danger, lien) · ouverture du contenu du lien dans une popup (au clic ou au survol) · position (par défaut, droite, toute la largeur) · ouvrir dans une nouvelle fenêtre (oui/non). (Pas d'équivalent au `nobtn` YesWiki : un bouton ne se rend pas en lien, les composants ne se mélangent pas.)

**Icônes (type `icon`)** : jeux Iconify **embarqués** — données `@iconify-json/{set}` installées par paquet, exposées via `icons.sets` dans la config (défaut : `lucide`, celui de l'UI). Un composant serveur en fait un **SVG inline** (`@iconify/utils`, `iconSvg()`) ; un composant client passe par le `<Icon>` client qui récupère le SVG de la route interne `GET /api/icons/[id]` (fetch same-origin, mis en cache) — les données d'icônes ne sont jamais bundlées côté client (ADR 0013). Dans les deux cas, **aucun appel réseau externe** : intranet et RGPD sereins. La prop stocke l'identifiant Iconify (`icon="lucide:settings"`). Le sélecteur (grille + recherche) cherche dans les jeux embarqués ; noms et tags Iconify étant anglophones, un avertissement discret le signale dans l'interface (lexique français de synonymes : backlog).

L'insertion se fait au curseur depuis le menu « Composants » de la barre d'outils (dropdown des `label`, tri alphabétique) ; la **réédition** suit le motif des outils ancrés de la v0.1 : curseur dans une balise de composant → crayon flottant → builder pré-rempli (mapping inverse), balise réécrite en place. Pas de crayon sur une balise malformée ou sans descripteur.

Composants couverts en v0.2 : **`Button`** (le bouton intégré), **`Image`**, **`Pdf`** (lecteur PDF du navigateur dans la page) et **`FileLink`** (lien de téléchargement : nom, taille) — chacun avec son descripteur co-localisé. `<Menu>` (wrapper) attend l'édition des composants à enfants, au backlog.

**Cas particulier `wiki-link`** : sa modale de paramétrage existait déjà, codée à la main dans le MVP. Elle est reconstruite sur le moteur ComponentBuilder avec son propre descripteur (champs : texte, cible `page-list`, ouverture), mais sa **cible de sérialisation** diffère : elle émet un lien markdown `[texte](cible){{ target: '…' }}` (ADR 0006), pas une balise JSX — c'est ce qui la tient hors du menu « Composants ». Ses portes d'entrée : le bouton « Ajouter un lien » de la barre d'outils et le bouton flottant d'édition de lien ancré au curseur.

## v0.3 — Formulaires & fiches

L'équivalent de **BazaR** : un **formulaire** définit une structure de champs, une **fiche** en est une instance saisie. ADR [0014](adr/0014-formulaires-et-fiches.md) (modèle) et [0015](adr/0015-shared-field-renderer-zod.md) (renderer partagé + Zod) ; spécification complète : [`forms.md`](forms.md).

**Le modèle en deux phrases.** *Un formulaire n'est pas une page* : c'est une définition (entité `Form`, écrite à l'exécution par le FormBuilder, jamais historisée — enregistrer écrase). *Une fiche est une page* : `Page.formId` renseigné, contenu porté par un snapshot JSON `data` sur la `Revision` au lieu du MDX `content` — slug, URL, révisions, restauration, tags et suppression sont la machinerie existante, pas une seconde. Supprimer un formulaire emporte ses fiches (cascade, confirmation annonçant le nombre) ; un schéma qui bouge **dégrade gracieusement** (clé orpheline préservée mais ignorée, champ nouveau vide) plutôt que de se versionner.

**Zod, contrat runtime** (ADR 0015). Un descripteur de composant est écrit dans le repo et vérifié au build (ts-morph, ADR 0013) ; un formulaire est écrit **à l'exécution**, sans `.tsx` ni build à confronter. Zod tient ce rôle au runtime, à trois endroits : méta-schéma validant le descripteur à l'enregistrement, schéma **dérivé** du formulaire validant les valeurs d'une fiche (le même client *et* serveur), types inférés pour le reste du code.

**Un renderer de champs partagé** (ADR 0015) : paramétrer un composant et saisir une fiche sont le même problème — rendre des champs typés depuis un descripteur, collecter des valeurs, valider. Le cœur (widgets, validation) est commun au ComponentBuilder, au FormBuilder et à la saisie ; seules diffèrent l'enveloppe et la sérialisation (MDX vs. JSON). Aucune bibliothèque de form-builder n'est introduite (analyse préalable : [`research/formulaires-fiches-architecture.md`](research/formulaires-fiches-architecture.md)).

**Les écrans** sont deux **pages spéciales** seedées dont le contenu appelle un composant intégré, comme `page-rapide-haut` : `formulaires` (`<FormsAdmin>` — liste, création, **FormBuilder**) et `fiches` (`<EntriesAdmin>` — toutes les fiches, celles d'un formulaire, saisie). Composants clients, état dans l'URL (`?id=`, `?formulaire=` — F5, retour arrière et liens directs fonctionnent), données chargées par **Server Action, y compris en lecture** (aménagement du triptyque handler/mutation/service).

**Le FormBuilder** rejoue le ComponentBuilder pour un descripteur JSON en base : palette de types → drag & drop (dnd-kit) vers le canvas, panneau de paramétrage par champ généré par le renderer partagé, éditeur de **gabarit** (CodeMirror + aperçu sur valeurs d'exemple), validation à l'enregistrement (méta-schéma, `name` uniques, `{champ}` du gabarit existants). 14 types de champs : texte court, texte long, email, url, date, liste, radio, cases à cocher, image, fichier, géolocalisation (Leaflet + Nominatim), mots-clés (= les tags de la Page), contenu personnalisé, titre. Les champs à options tirent leurs valeurs *inline* ou **des fiches d'un autre formulaire** (`sourceFormId` : valeur stockée = slug de la fiche cible, rendue en lien wiki).

**Saisie et rendu d'une fiche.** Trois portes, un seul formulaire généré : `<EntryForm id="…" />` posé dans n'importe quelle page, `/fiches?nouvelle&formulaire=…`, ou `/{slug}/edit` d'une fiche (le handler `edit` ouvre le formulaire pré-rempli, jamais CodeMirror). La soumission valide avec le même schéma Zod des deux côtés puis crée une `Revision`. Au `show`, deux voies selon `Form.template` : **rendu par défaut** auto-généré depuis le schéma, ou **gabarit MDX** dont les `{champ}` sont substitués **avant compilation** puis passés au pipeline sandboxé. Les valeurs injectées sont du **texte brut** — celui qui remplit une fiche ne peut ni injecter de composants ni casser la mise en page ; les deux exceptions (`customContent`, `textarea` en `allowMdx`) sont des décisions de l'admin du formulaire.

**Identités** : `Form.slug`, `name` de champ et slug de fiche suivent la même règle — dérivé automatiquement, éditable en place avant enregistrement (chip), puis **figé**. Nouveau service d'API au passage : `GET /api/files/{nom}?w=…&h=…`, redimensionnement à la demande (sharp) avec cache disque, l'original restant intact.

**En cours de route.** Deux chantiers non prévus, tous deux généralisés au-delà des fiches :

- **Colmatage du bac à sable** (ADR 0002) : liste blanche de **balises HTML** autorisées, refus par nom de `dangerouslySetInnerHTML` et de `srcDoc`, et composant `<Embed>` (devenu `<Iframe>` en v0.4) à côté du collage d'`<iframe>`.
- **« Changer l'adresse »** (ADR [0016](adr/0016-slug-rename-rewrites-references.md)) : renommer un slug de page ou de fiche **réécrit toutes les références**, historique compris, sans redirection — l'ancienne adresse cesse d'exister. Même geste pour l'identifiant d'un formulaire (immédiat) et d'un champ, ce dernier **différé à l'enregistrement** du formulaire (ADR [0017](adr/0017-field-rename-staged-at-form-save.md)).

## v0.4 — EntriesView

La famille d'actions `bazar…` de YesWiki (`bazarliste`, `bazarcard`, `bazarcarto`…) en **un seul composant intégré** : `<EntriesView>` affiche les fiches d'un ou plusieurs formulaires selon **neuf vues** — Liste, Grille, Tableau, Carte, Calendrier, Agenda, Annuaire, Carrousel, Galerie photo. ADR [0018](adr/0018-entries-view-descriptor-driven.md) et [0019](adr/0019-structured-props-literal-expressions.md) ; spécification complète (dont la table de migration YesWiki → WikiOui) : [`entries-view.md`](entries-view.md).

- **Toujours interactif** : la distinction YesWiki statique/dynamique disparaît. Recherche, filtres, tri, compteurs et pagination s'exécutent **en mémoire côté client** (latence zéro), sur des fiches chargées d'un coup par une Server Action de lecture qui ne renvoie que les **champs référencés** par la configuration. Le filtrage serveur reste une optimisation interne possible, sans changer la balise.
- **Paramètres communs à toutes les vues** : zones (Titre, Sous-titre, Texte, Pied, Visuel, Légende, Badge), recherche, **Filtres disponibles** (ex-« facettes », compteurs en direct, bouton « Effacer les filtres » automatique), tri (dont tris proposés aux visiteurs), sélection des fiches (période, maximum), pagination, **couleur & icône par champ** (palette automatique dès le choix du champ, surcharges au color picker), et « **Lors du clic, afficher la fiche** » : popup par défaut — le rendu `show` réel de la fiche, sans chrome, restituant l'état exact à la fermeture.
- **Multi-formulaires sans mode** : « + Ajouter les fiches d'un autre formulaire » fait apparaître un second sélecteur ; les champs proposés deviennent l'union dédoublonnée par `name`. Des **pseudo-champs** préfixés `$` (`$form`, `$owner`, `$createdAt`, `$editedAt`) côtoient les vrais champs sans collision possible.
- **Le builder reste 100 % descripteur** (ADR 0018) : plutôt qu'une modale codée à la main pour un composant à ~40 props, le vocabulaire de champs gagne six types génériques réutilisables — `view-picker` (tuiles), `form-field` (champs des formulaires choisis, options chargées selon le champ frère), `field-rows` (lignes ordonnées champ + titre éditable), `color-mapping`, `icon-mapping`, `map-view`.
- **Props structurées en expressions littérales JSX** (ADR 0019) : `filters={[{ field: "type", title: "Type de structure" }]}` — le bac à sable les rendait déjà (`lib/mdx-literal-props.ts`), le chantier a été le **round-trip** du builder (parser l'AST du littéral, le régénérer). C'est aussi ce qui permet `form={["associations", "evenements"]}` sur la même prop que le cas mono-formulaire.
- **Bibliothèques arrêtées à l'implémentation** : FullCalendar 7 (thème re-mappé sur les tokens WikiOui), Embla (carrousel), Leaflet + `leaflet.markercluster` (carte) ; tableau et visionneuse **faits main** — le pipeline en mémoire possède déjà tri et pagination, une seconde machinerie aurait fait deux sources de vérité.

Trois chantiers hors périmètre initial :

- **Titre automatique calculé à l'écriture** (ADR [0020](adr/0020-automatic-title-stored-at-write.md)) : le titre d'une fiche en mode automatique était recalculé à chaque lecture (illisible pour trier, filtrer ou chercher côté base). Il est désormais **stocké dans `data`** comme toute valeur de champ, injecté côté serveur après validation, recalculé en masse quand le gabarit bouge (nouvelle révision par fiche changée, derrière confirmation) et garanti non vide par une contrainte en base.
- **Rendu chrome-free** (ADR [0022](adr/0022-chrome-free-iframe-handler-and-wikiframe.md)) : handler `/{slug}/iframe` dans un groupe de routes `(bare)`, brique `WikiFrame` partagée, et `<Embed>` renommé en **`<Iframe>`** — il embarque désormais aussi bien une page du wiki (auto-dimensionnée) que le site d'un tiers.
- **Déploiement** (ADR [0021](adr/0021-docker-standalone-migrate-seed-on-start.md)) : image Docker en sortie `standalone`, outils Prisma isolés, `migrate` à chaque démarrage et seed une seule fois. Guide VPS pas à pas : [`deployment-dokploy.md`](deployment-dokploy.md).

## v0.5 — Utilisateurs & droits

La gestion des droits de YesWiki, refondue pour tenir sans documentation. ADR [0023](adr/0023-betterauth-authentifie-wikioui-autorise.md) à [0028](adr/0028-tout-ecran-est-une-page.md) ; spécification complète : [`permissions.md`](permissions.md).

**Le modèle en deux phrases.** *BetterAuth authentifie, WikiOui autorise* (ADR 0023) : la bibliothèque sait qui vous êtes, elle ne sait rien de ce que vous avez le droit de faire — ni le plugin `admin` (qui imposerait un champ `role` là où l'administration est une **appartenance** au groupe `@Admins`) ni `organization` (qui n'imbrique pas les groupes et ignore nos portées) ne sont utilisés ; seul `username` l'est, parce qu'il relève de l'authentification. *Un droit est une **portée**, éventuellement complétée d'une liste* : tout le monde · les personnes connectées · seulement — le propriétaire et les administrateurs étant toujours autorisés, et ne figurant donc jamais dans la liste.

- **Trois niveaux d'accès** — visiteur, utilisateur, administrateur — qui ne se paramètrent pas : ils se constatent. Pas de colonne de rôle nulle part. Un **acteur** est la personne qui agit, à l'un de ces trois niveaux.
- **Quatre étages de droits**, un seul widget : page/fiche · formulaire (créer une fiche, plus les deux droits par défaut d'une fiche — les distinguer est ce qui permet « chacun propose, chacun ne modifie que le sien ») · champ (le serveur **fusionne** au lieu de remplacer, et le titre automatique ne peut pas référencer un champ restreint) · configuration. Le sélecteur devient un **type de descripteur `acl`**, rendu par le renderer partagé (ADR 0015) — obligatoire, puisque les droits par champ vivent dans le panneau du FormBuilder.
- **Les défauts se recopient, jamais ne se lient** (ADR 0026) : modifier un défaut ne touche rien de l'existant ; « Appliquer aux fiches existantes » est le seul chemin, à confirmation chiffrée.
- **Les droits désignent des `username` et des `groupSlug`** (ADR 0024), avec `onDelete: Cascade` sur les lignes d'ACL et d'appartenance, mais **`SetNull`** sur la propriété et l'auteur — la même cascade y détruirait des pages et des pans d'historique. Aucune FK n'entrant dans du JSON, les droits par champ exigent un balayage applicatif au renommage *et* à la suppression, de la facture des ADR 0016/0017.
- **Une seule porte** (ADR 0025) : `lib/pages.ts` et `lib/forms.ts` résolvent eux-mêmes l'acteur courant, et une règle ESLint interdit l'accès direct — même esprit que la vérification au `prebuild` de l'ADR 0013. Écartés : Row-Level Security (deux rôles Postgres et des transactions interactives imposés à chaque déploiement) et l'extension Prisma (ne couvre pas l'écriture). Le filtrage est une clause `WHERE`, y compris pour `<EntriesView>` ; seuls les champs se filtrent en mémoire, le JSON étant hors de portée du SQL.
- **Deux écrans** : `gerer-utilisateurs` (comptes, invitations par lot digérant ce que crache un client mail, groupes et leur imbrication expliquée avec le chemin cliquable) et `gerer-pages` (recherche, filtres, lot en deux intentions — « Remplacer les accès » ou « Donner accès », qui n'enlève l'accès à personne et annonce combien de pages y donnent déjà accès).
- **Ce qui manque ne se devine pas** : action masquée, bloc de contenu expliqué et actionnable, champ grisé avec son motif. Rien ne disparaît automatiquement d'un menu — c'est l'auteur qui pose `hideIfNoAccess` sur un lien, un bouton ou une iframe, via le `showif` en lookahead qui masque le paramètre dès qu'on tape `https://`.
- **Amorçage** : un écran d'installation gardé par un drapeau **irréversible** (ADR 0027) plutôt que par l'absence d'administrateur, qui en ferait un chemin d'escalade. Nouveau handler `/{slug}/raw` au passage (MDX ou JSON brut, champs non lisibles retirés avant sérialisation).
- **Les écrans de comptes sont des pages** (ADR 0028) : `connexion`, `inscription`, `mot-de-passe-oublie` et `invitation` sont des pages spéciales appelant un composant intégré, comme les écrans d'administration avant elles — le jeton d'un lien à usage unique voyage en `?jeton=`, un segment derrière un slug étant un handler. L'installation elle-même n'ajoute aucune route de niveau 1 : elle doit répondre avant qu'aucune page ne soit lisible, vit donc sous `/api` et se présente par réécriture, laissant le slug `installation` à qui voudra une page de ce nom. Ces quatre pages restent lisibles par tout le monde quel que soit le droit posé : la connexion doit répondre là où le contenu refuse.

## Architecture en un coup d'œil

- **Routing** (ADR 0001) : les handlers sont des routes Next natives. `app/(site)/[slug]/page.tsx` = `show` ; `app/(site)/[slug]/edit/page.tsx`, `app/(site)/[slug]/revisions/page.tsx` — le groupe `(site)` est invisible dans l'URL, il porte le layout du chrome (bandeau, menu, footer) ; le layout racine est réduit au squelette (`html`/`body`/polices), ce qui permet des pages nues sous `/api`. Le handler **`/{slug}/iframe`** (rendu sans chrome, embarqué en iframe — ADR 0022) vit dans un groupe **`(bare)`** frère de `(site)` pour échapper au chrome tout en restant un handler `/{slug}/{handler}`. `/` redirige vers `/page-principale` (`redirects()`). Slug : `^[a-z0-9]+(?:-[a-z0-9]+)*$`, minuscules (majuscules redirigées), tapé dans l'URL (pas de titre séparé) ; renommable par « Changer l'adresse » (ADR 0016), sans redirection.
- **Handler de page vs Mutation vs Service d'API** : un handler de page *affiche* une vue (`/{slug}/{handler}`) ; sauvegarder / supprimer / restaurer / renommer sont des **Server Actions** (pas d'URL) ; les **Services d'API** (sous le segment réservé `/api`) servent le code — `GET /api/files/[name]` (avec `?w=&h=` : variantes sharp en cache disque), `POST /api/files` (mutation portée par un service : la progression d'upload, ADR 0012), `GET /api/icons/[id]`, en `route.ts` ; `GET /api/render` (aperçu des builders) est le cas particulier du service dont la réponse est une page HTML complète, porté par une `page.tsx` nue. Depuis la v0.3, une Server Action porte aussi des **lectures** pour les composants clients (écrans d'administration, chargement des fiches d'EntriesView) — même transport, mais ce n'est pas une mutation.
- **Rendu** (ADR 0002) : MDX bridé par **trois listes blanches**, une par chose qu'un auteur écrit — les composants (registre = `/components/wiki` en autodécouverte + config), les **balises HTML** (`lib/mdx-host-elements.ts` : ce qui met en forme de la prose, plus `iframe` ; `script`, `style`, `object`, `embed`, `form`, `link` dehors, avec leurs enfants), et les **valeurs de props** (`lib/mdx-literal-props.ts` : littéraux statiques — une prop reçoit ainsi un vrai nombre, ou l'objet littéral d'une prop structurée d'EntriesView, sans ouvrir de RCE). S'y ajoutent `import`/`export` désactivés, les expressions JS de contenu supprimées, et **deux refus par nom** : `dangerouslySetInnerHTML` (sa charge `{__html: '…'}` est un objet littéral valide — seule la lecture du nom par React en fait du balisage) et `srcDoc` (tout le risque d'`<iframe>` : son contenu hérite de notre origine et y exécute ses scripts, alors qu'un `src` cross-origin est muré par la politique de même origine). La liste des balises ne porte que sur le JSX **tapé par l'auteur** : le HTML produit par markdown naît de nœuds mdast qui ne passent pas par le chemin JSX. Embarquer un site tiers a donc deux portes, une par geste : **coller** l'extrait tout fait de YouTube ou d'OSM (`<iframe>`, qui passe verbatim — les noms d'attributs HTML sont normalisés vers leurs noms JSX, sans quoi `allowfullscreen` serait mangé), ou **construire** via le composant `<Iframe>` du menu (ADR 0022), qui ajoute `https`, `sandbox` sans `allow-top-navigation` et un `title`. Le rendu d'une **fiche** emprunte ce même pipeline : gabarit substitué (valeurs échappées en texte brut) ou rendu par défaut, jamais un second moteur.
- **Contrôle à l'enregistrement** : ce que le rendu laisse tomber en silence est annoncé à l'auteur avant d'enregistrer (`lib/page-lint.ts` via l'action `lintPage` : le premier « Enregistrer » analyse sans écrire, un panneau liste les problèmes avec un lien vers chaque ligne, « Enregistrer quand même » passe outre) : balise HTML non autorisée, composant inconnu, propriété inconnue, propriété requise manquante, valeur hors options, valeur qui n'honore pas le type déclaré (`propKind`, une règle pour tous les types), lien vers une page inexistante. La référence est le **contrat du descripteur**, pas ce qu'un composant tolère : `width="200"` rend correctement — `<Image>` s'en sort parce qu'`imageUrl` fait `String()` dessus — mais reste signalé, car `type: number` promet un nombre et un autre composant faisant `width.toFixed(0)` planterait. Le champ du builder est ce contrat en code, et l'étalon : il affiche cette largeur **vide**. Sont donc signalés `width="200"`, `width="abc"`, `width` nu, et `whiteBorder="false"` (toute chaîne non vide étant vraie, elle active le bord). Une source qui ne parse pas devient elle-même l'avertissement (les mots du compilateur vont dans `details`, affichés en monospace) : elle ne bloque jamais l'enregistrement. Écartés délibérément : **le crayon sur une balise malformée** (`<Image width= />`) — il faudrait deviner où la balise s'arrête, or cette étendue sert à écraser du texte, et une erreur passerait de « pas de crayon » à « texte détruit » ; le panneau donne la ligne, cela suffit. Et le **contrôle des fichiers absents du pool ou de mauvaise famille** — un auteur écrit légitimement sa page avant d'uploader.
- **Descripteurs** : un même vocabulaire de champs décrit ce qu'un auteur paramètre, quelle que soit l'origine du descripteur — **YAML du repo** pour un composant (vérifié par signature au build, ADR 0013) ou **JSON en base** pour un formulaire (vérifié par méta-schéma Zod au runtime, ADR 0015). Le renderer qui les rend est le même, et chaque nouveau type de champ (ADR 0018) profite aux deux.
- **Éditeur** (ADR 0005) : CodeMirror 6, édition de source MDX colorée. Barre d'outils : gras, italique, barré, titres, listes (puces/numérotée/tâches), citation, code, ligne horizontale, alignement (classe Tailwind), commentaire (`{/* */}`), lien (modale), insertion de tableau, aide-mémoire. Pas de souligné. UI contextuelle **ancrée au curseur** (tooltips CodeMirror) : icône de modification de lien, opérations de tableau positionnées spatialement (colonne en haut, ligne à gauche, reformatage au coin). Double-clic sur le contenu du `show` → édition. Une **fiche** n'en relève pas : son `edit` est le formulaire généré.
- **Liens** (ADR 0006) : liens wiki en relatif par slug (`[texte](ma-page)`) ; externes en `http(s)://`. Modale de lien : cible onglet courant / nouvel onglet / **fenêtre modale** (Dialog ; avertissement si URL externe). Autocomplétion des pages. Depuis la v0.2, cette modale est un ComponentBuilder généré depuis `components/wiki/wiki-link.yaml`, à sérialisation markdown.
- **Pages spéciales** : slug réservé, seedées, non supprimables ni renommables mais éditables — les 5 de layout, `page-principale`, `aide-memoire`, depuis la v0.3 `formulaires` et `fiches` (dont le contenu appelle `<FormsAdmin>` / `<EntriesAdmin>`), et depuis la v0.5 `gerer-utilisateurs` (`<UsersAdmin>` + `<GroupsAdmin>`) et les quatre écrans de comptes `connexion`, `inscription`, `mot-de-passe-oublie`, `invitation` (`<SignIn>`, `<SignUp>`, `<ForgotPassword>`, `<Invitation>`).
- **Tout écran est une page** (ADR 0028) : un écran neuf est une page spéciale appelant un composant intégré, jamais une route sous `app/` — celle-ci prélèverait un slug sans le dire. Ce dont l'écran a besoin voyage en query string (`?suite=`, `?jeton=`, `?formulaire=`), puisque derrière un slug un segment est un handler. Seule exception, le segment réservé `api` : il porte les services, et les deux écrans qui ne peuvent pas être des pages — l'aperçu du ComponentBuilder et l'installation (`/api/installation`, présentée par **réécriture** depuis n'importe quelle adresse tant que le drapeau manque, ce qui laisse `installation` libre comme slug). `api` est le seul slug que `lib/slug.ts` refuse à une page, et `app/routes.test.ts` rougit dès qu'un dossier de plus apparaît sous `app/`.
- **Historique** (ADR 0009) : pleine page, timeline horizontale (récente à droite), toutes les révisions. 3 vues : *Aperçu* (checkbox rendu ↔ code), *Modifications* (diff MDX vs précédente), *Différence avec la courante* (diff MDX). Diffs sur le source uniquement. Pour une fiche, la révision porte `data` au lieu de `content` ; restaurer recalcule le titre automatique (ADR 0020) plutôt que de le recopier.
- **Config** (ADR 0004) : `wiki.config.ts` typé — slugs des pages spéciales et slug d'accueil, `upload.*` (tailles limites et extensions par famille), `icons.sets` (jeux Iconify exposés), composants déclarés hors `/components/wiki`.

## Schéma Prisma

Schéma Prisma : [prisma/schema.prisma](../prisma/schema.prisma) — trois modèles : `Form`, `Page`, `Revision`.

Notes : création d'une page en deux temps (Page → Revision → pointer `currentRevisionId`). ## Points validés avant code

- **`remark-attributes` → remplacé par `mdx-annotations`** (validé le 2026-07-08). `remark-attributes` exige des accolades échappées `\{…\}` sous MDX (contrainte du parseur MDX, rédhibitoire pour les auteurs). `mdx-annotations` (Tailwind Labs) exploite les expressions MDX à la place : `# Titre {{ id: 'ancre' }}`, `[lien](/page){{ className: 'btn' }}` — zéro échappement, vérifié sous MDX 3 / next-mdx-remote 6. Les conteneurs/encarts passent par le registre de composants (ADR 0002), sans `remark-directive` (une seule syntaxe avancée : le JSX ; la directive reste ajoutable plus tard, coexistence prouvée). Preuves : [`research/remark-attributes-mdx.md`](research/remark-attributes-mdx.md), [`research/mdx-native-element-attributes.md`](research/mdx-native-element-attributes.md).
- **Descripteur ComponentBuilder → YAML seul, composants sans contrat, vérifié par signature** (validé le 2026-07-12, ADR 0013). Les défauts ont quitté le `.tsx` (l'export `xxxDefaults` forçait le composant serveur, cf. le bug du menu commit `67ffd53`) pour le YAML ; le composant est devenu du React ordinaire, client ou serveur. La cohérence YAML ↔ composant (champ ∈ props, obligatoire, type, dérive du `default`, type de `value`) est vérifiée en parsant la **source** du composant (`ts-morph`, *devDependency*, `lib/verify-descriptors.ts`), au build (`prebuild` bloquant) et en dev (overlay d'erreur au chargement de l'éditeur), jamais au runtime de prod. Changement compagnon : route d'icônes `GET /api/icons/[id]` + `<Icon>` client, qui a permis de repasser `<Button>` en composant client — supprimant à la racine la classe de bug du `<button>` imbriqué du menu.
- **Aucune bibliothèque de form-builder** (validé le 2026-07-12, ADR 0014/0015). SurveyJS, Form.io, `react-form-builder2` et `@autoform/react` apportent leur propre moteur de rendu, leur thème et parfois leur stockage — collision frontale avec shadcn/Tailwind et avec l'architecture de descripteurs. Le renderer de champs du ComponentBuilder *est* déjà un « schéma → formulaire », mieux adapté (types riches `page-list`, `file-list`, `icon`, moteur `showif`). Analyse : [`research/formulaires-fiches-architecture.md`](research/formulaires-fiches-architecture.md).
